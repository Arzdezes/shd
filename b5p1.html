Лабораторная работа 1: Настройка Samba-сервера и клиента

Тема: Развёртывание Samba-сервера на ALT Server, настройка публичных и защищённых шары, подключение с ALT Workstation, эксперименты с правами доступа и протоколами SMB.

Цель работы: Научиться настраивать Samba-сервер в режиме standalone, создавать ресурсы с различными уровнями доступа, подключать их с клиента Linux, понимать разницу между гостевым доступом и аутентификацией, а также отработать настройку прав доступа на уровне файловой системы и Samba.

Топология:

  • Сервер: ALT Server 11 (виртуальная машина)
  • Клиент: ALT Workstation 10.4 (хостовая система)

Подготовка

Важно: Для выполнения команд с правами администратора мы будем использовать su -.
Переключитесь в режим root на обеих машинах.

На сервере (ALT Server)

su -

На клиенте (ALT Workstation)

su -

1.1 Проверка сетевого взаимодействия

Прежде чем настраивать Samba, убедимся, что сервер и клиент видят друг друга.

На сервере:

ip a

Запомните IP-адрес сервера (например, 192.168.122.206).

На клиенте:

ping -c 3 <IP-адрес_сервера>

1.2 Установка необходимых пакетов

На сервере (ALT Server 11):

ALT Server 11 поставляется с Samba версии 4.21.9. Установим серверную часть:

apt-get update
apt-get install samba samba-client samba-test

Пояснение: Пакет samba содержит серверную часть (демоны smbd и nmbd), а samba-client и samba-test — клиентские утилиты для тестирования.

На клиенте (ALT Workstation):

Для монтирования Samba-шар с Linux-клиента необходим пакет cifs-utils:

apt-get update
apt-get install cifs-utils samba-client

Пояснение: cifs-utils содержит утилиту mount.cifs для монтирования SMB-ресурсов. samba-client установим для диагностики (smbclient, smbstatus).

1.3 Проверка установки

На сервере:

systemctl status smb
systemctl status nmb

Вопрос: В каком состоянии находятся сервисы? Если они не активны, как их запустить?

Пояснение: Сервисы smb (основной файловый сервер) и nmb (NetBIOS name server, для обнаружения в сети) должны быть активны. Запустите их, если нет: systemctl enable --now smb nmb.

Этап 2: Создание каталогов для шары и тестовых данных

2.1 Создание каталогов с разными сценариями доступа

На сервере:

Создадим три каталога для демонстрации разных режимов доступа:

Публичная шара (только чтение для всех)

mkdir -p /srv/samba/public
echo "Public file - доступен всем" > /srv/samba/public/readme.txt

Шара для чтения-записи с аутентификацией

mkdir -p /srv/samba/private
echo "Private area ready" > /srv/samba/private/welcome.txt

Upload-зона (гостевой доступ на запись)

mkdir -p /srv/samba/upload
echo "Upload area ready" > /srv/samba/upload/welcome.txt

Вопрос: Как вы думаете, почему для upload-зоны мы создаём отдельный каталог? Какие права нужно будет выставить?

2.2 Настройка прав доступа

Добавим группу sambashare

groupadd sambashare

Для публичной шары — права на чтение для всех

chmod 755 /srv/samba/public

Для приватной шары — доступ только для владельца и группы

chown root:sambashare /srv/samba/private
chmod 770 /srv/samba/private

Для upload-зоны — все могут писать, но не удалять чужие файлы (sticky bit)

chmod 1777 /srv/samba/upload
Пояснение: Sticky bit (chmod 1777) на каталоге upload гарантирует, что пользователь может удалить только свои файлы, даже если имеет право на запись в каталог. Это стандартная практика для upload-каталогов.

2.3 Создание пользователей для аутентификации

Создаём системного пользователя (должен существовать в системе)

useradd -m -s /bin/bash smbuser
passwd smbuser  # Установите пароль (например, "password")

Добавляем пользователя в группу sambashare

usermod -aG sambashare smbuser

Добавляем пользователя в базу паролей Samba

smbpasswd -a smbuser

Пояснение: Samba использует отдельную базу паролей (smbpasswd), не зависящую от системных паролей. Пользователь с системным аккаунтом smbuser и его пароль Samba могут отличаться.

Вопрос: Зачем нужна отдельная база паролей? Как это связано с безопасностью?

Этап 3: Настройка Samba (/etc/samba/smb.conf)

3.1 Резервное копирование конфигурации

cp /etc/samba/smb.conf /etc/samba/smb.conf.bak

3.2 Редактирование конфигурационного файла

Откроем /etc/samba/smb.conf для редактирования:

mcedit /etc/samba/smb.conf
или 
nano /etc/samba/smb.conf

Приведём файл к следующему виду:

[global]
    workgroup = WORKGROUP
    server string = ALT Samba Server
    security = user
    map to guest = Bad User
    log file = /var/log/samba/log.%m
    max log size = 50
    
    # Кодировки для корректной работы с русскими именами файлов
    unix charset = UTF-8
    dos charset = CP866
    
    # Оптимизация производительности
    socket options = TCP_NODELAY IPTOS_LOWDELAY
    read raw = yes
    write raw = yes

# Публичная шара (только чтение, гостевой доступ)
[public]
    comment = Public Share
    path = /srv/samba/public
    browseable = yes
    read only = yes
    guest ok = yes
    create mask = 0644
    directory mask = 0755

# Приватная шара (доступ по паролю)
[private]
    comment = Private Share
    path = /srv/samba/private
    browseable = yes
    read only = no
    guest ok = no
    valid users = smbuser
    create mask = 0660
    directory mask = 0770

# Upload-зона (гостевой доступ на запись)
[upload]
    comment = Upload Area
    path = /srv/samba/upload
    browseable = yes
    read only = no
    guest ok = yes
    create mask = 0666
    directory mask = 0777

Вопрос: Проанализируйте каждую секцию. Что означают опции browseable, guest ok, valid users, create mask?

Пояснение:

  • map to guest = Bad User — неверные логины автоматически перенаправляются на гостевой доступ (важно для upload-зоны)
  • create mask / directory mask — права, с которыми создаются новые файлы и папки внутри шары
  • valid users — список пользователей, имеющих доступ к шаре.

3.3 Проверка конфигурации

testparm
Пояснение: testparm проверяет синтаксис конфигурационного файла и показывает итоговую конфигурацию после обработки всех включений и переменных.

3.4 Применение конфигурации

Перезапускаем сервисы

systemctl restart smb nmb
Пояснение: Для применения изменений достаточно перезапустить сервисы. В ALT Linux это systemctl restart smb nmb.

Этап 4: Локальная проверка на сервере

4.1 Проверка доступности ресурсов

Список всех доступных ресурсов на сервере

smbclient -L localhost -N
Вопрос: Какие ресурсы вы видите? Почему private не показывается при анонимном подключении?

4.2 Проверка подключения к разным ресурсам

Подключение к публичной шаре

smbclient //localhost/public -N

Внутри интерактивной оболочки выполните:

ls
exit

Подключение к приватной шаре

smbclient //localhost/private -U smbuser

Внутри оболочки:

mkdir test_folder
ls
exit

Вопрос: Удалось ли создать папку в приватной шаре? Почему?

Подключение к upload-зоне

smbclient //localhost/upload -N

Внутри оболочки:

mkdir test_upload
put /etc/hosts hosts_copy.txt
ls
exit
Пояснение: smbclient — это FTP-подобный клиент для тестирования SMB-ресурсов. Команда -N означает "без пароля" (гостевой доступ).

Этап 5: Подключение с клиента (ALT Workstation)

5.1 Создание точек монтирования

На клиенте:

mkdir -p /mnt/samba/public
mkdir -p /mnt/samba/private
mkdir -p /mnt/samba/upload

5.2 Монтирование публичной шары (гостевой доступ)

mount -t cifs //<IP-сервера>/public /mnt/samba/public -o guest,vers=3.0
Пояснение: Опция guest означает анонимное подключение. Протокол vers=3.0 указывает использование SMB 3.0.

5.3 Монтирование приватной шары (с аутентификацией)

Простой способ: пароль в командной строке (небезопасно, но для теста приемлемо)

mount -t cifs //<IP-сервера>/private /mnt/samba/private -o username=smbuser,password=password,vers=3.0
Вопрос: Почему передавать пароль в командной строке небезопасно?

Безопасный способ: через файл учётных данных:

Отмонтируем шару

umount /mnt/samba/private

Создаём файл с учётными данными

cat > /root/.smbcredentials << EOF
username=smbuser
password=password
domain=WORKGROUP
EOF

Ограничиваем доступ к файлу

chmod 600 /root/.smbcredentials

Монтируем с использованием файла

mount -t cifs //<IP-сервера>/private /mnt/samba/private -o credentials=/root/.smbcredentials,vers=3.0
Пояснение: Файл учётных данных должен быть доступен только root, так как содержит пароль в открытом виде. Какой способ лучше?

5.4 Монтирование upload-зоны

mount -t cifs //<IP-сервера>/upload /mnt/samba/upload -o guest,vers=3.0

5.5 Проверка монтирования

df -h | grep samba
mount | grep cifs
Пояснение: df -h покажет точки монтирования и использованное место. mount | grep cifs — более детальную информацию о смонтированных SMB-ресурсах.

6.1 Проверка публичной шары (только чтение)

На клиенте:

Чтение — должно работать

Запись — должна завершиться ошибкой

6.2 Проверка приватной шары (чтение-запись)

Чтение

Запись

echo "secret data" > /mnt/samba/private/secret.txt

6.3 Проверка upload-зоны (гостевая запись)

Запись от имени гостя

echo "uploaded by guest" > /mnt/samba/upload/guest_file.txt

Создание папки от имени гостя

6.4 Проверка механизма маппинга пользователей

На сервере: (в другом терминале или после завершения):

Кто владелец файлов, созданных через upload-шару?

ls -la /srv/samba/upload/

Вопрос: Кто является владельцем файлов, загруженных в upload-шару? Почему не smbuser?

Пояснение: При гостевом доступе (guest ok = yes) Samba маппит всех пользователей на анонимного (обычно nobody), если не задан force user. Это важно для безопасности.

Этап 7: Дополнительные эксперименты

7.1 Наблюдение за активными соединениями

На сервере:

smbstatus
Пояснение: smbstatus показывает текущие подключения, открытые файлы и блокировки.

7.2 Монтирование с разными версиями протокола

На клиенте: (сначала отмонтируйте upload-шару):

umount /mnt/samba/upload

Монтируем с SMB 2.0

mount -t cifs //<IP-сервера>/upload /mnt/samba/upload -o guest,vers=2.0

Проверяем версию протокола

mount | grep upload

Вопрос: Чем отличается SMB 2.0 от SMB 3.0? Почему рекомендуется использовать более новые версии?

Пояснение: ALT Server 11 поддерживает SMB 3.0 с улучшенным шифрованием и производительностью. Для безопасности рекомендуется использовать vers=3.0 или выше.

7.3 Блокировка файла

На клиенте:

nano /mnt/samba/upload/guest_file.txt

На сервере:

smbstatus

На клиенте:

Ctrl+X

Пояснение: nano создает временный файл .guest_file.txt.swp и открывает его на запись. Что и отображает smbstatus в секции Locked files.

Этап 8: Очистка

На клиенте:

Размонтируем всё

umount /mnt/samba/public
umount /mnt/samba/private
umount /mnt/samba/upload

Удаляем временные файлы (опционально)

rm -f /root/.smbcredentials

На сервере:

Останавливаем Samba (по желанию)

systemctl stop smb nmb

Удаляем пользователя Samba

smbpasswd -x smbuser
userdel -r smbuser
groupdel sambashare

Удаляем каталоги

rm -rf /srv/samba

Возвращаем конфиг по умолчанию (по желанию)

mv -f /etc/samba/smb.conf.bak /etc/samba/smb.conf

Выводы

  • Samba — мощная реализация протоколов SMB/CIFS, позволяющая организовать файловый сервер в Linux-среде.
  • ALT Server 11 использует Samba 4.20 с поддержкой SMB 3.0, улучшенным шифрованием и производительностью
  • Настройка Samba требует внимания к двум уровням прав: файловая система Linux (права на каталог) и конфигурация Samba (read only, valid users, create mask).
  • Гостевой доступ (guest ok = yes) удобен для публичных ресурсов, но требует осторожности — все операции выполняются от имени анонимного пользователя.
  • Для аутентификации необходимо создать системного пользователя и добавить его в базу smbpasswd
  • Для монтирования с Linux-клиента используется пакет cifs-utils и команда mount -t cifs с указанием версии протокола
  • Для автоматического монтирования при загрузке используются записи в /etc/fstab с опцией _netdev.
