Лабораторная работа №2: Масштабирование S3-кластера MinIO

Тема: Горизонтальное масштабирование объектного хранилища, отказоустойчивость и Erasure Coding в распределённом кластере MinIO.

Цель работы: Продемонстрировать легкость горизонтального масштабирования S3-совместимого хранилища путём добавления новых серверов в кластер, изучить механизмы отказоустойчивости (Erasure Coding) и убедиться, что данные остаются доступными при отказе узлов.

Топология:

  • MinIO Server 1: ALT Server 11 (ВМ1) — 192.168.56.108
  • MinIO Server 2: ALT Server 11 (ВМ2) — 192.168.56.109 (клон ВМ1)
  • MinIO Server 3: ALT Server 11 (ВМ3) — 192.168.56.110 (клон ВМ1)
  • Клиент: ALT Workstation (хост) — 192.168.56.1

Особенности сетевой настройки:
В лабораторной среде VirtualBox используется сеть типа "Внутренняя сеть" / "Host-Only" с диапазоном 192.168.56.0/24. DHCP в этой сети выдаёт адреса ВМ последовательно.

Подготовка

Важно: Для выполнения команд с правами администратора мы будем использовать su -.
Переключитесь в режим root на обеих машинах.

1.1 Клонирование и подготовка серверов

Перед началом работы создайте два клона первой виртуальной машины (с уже установленным Docker и настроенным MinIO). После клонирования измените сетевые настройки на каждой ВМ:

На ВМ2 (клон 1):

su -

Меняем IP-адрес

nano /etc/net/ifaces/eth0/ipv4address

Меняем 192.168.56.108 на 192.168.56.109

Перезапускаем сеть

systemctl restart network

Проверяем

ip a | grep 192.168.56

На ВМ3 (клон 2):

su -

Меняем IP-адрес

nano /etc/net/ifaces/eth0/ipv4address

Меняем 192.168.56.108 на 192.168.56.110

Перезапускаем сеть

systemctl restart network

Проверяем

ip a | grep 192.168.56

Пояснение: Клонирование ВМ — это и есть демонстрация лёгкости масштабирования в виртуальной среде. За несколько минут мы получаем новые серверы, готовые войти в кластер. Важно, чтобы все серверы были в одной сети и видели друг друга.

На клиенте (ALT Workstation):

На ВМ1

Пояснение: Все серверы должны видеть друг друга по сети. Это критически важно для формирования кластера.

1.3 Остановка существующих контейнеров и подготовка дисков

На каждом сервере (ВМ1, ВМ2, ВМ3):

Останавливаем и удаляем существующий контейнер (если запущен)

docker stop minio-server 2>/dev/null
docker rm minio-server 2>/dev/null

Создаём директории для данных (по 4 на каждом сервере)

mkdir -p /data/minio/disk{1,2,3,4}

Пояснение: Для демонстрации Erasure Coding на каждом сервере нужно несколько дисков (или их эмуляций). MinIO рекомендует использовать как минимум 4 диска на сервер для оптимальной конфигурации. У нас будет 3 сервера × 4 диска = 12 дисков в кластере.

Вопрос: Что произойдёт, если запустить только один сервер с такой командой? Почему MinIO требует, чтобы все серверы кластера были указаны при запуске?

Пояснение: MinIO использует протокол консенсуса для координации состояния кластера. При запуске все узлы должны знать друг о друге. Это позволяет автоматически формировать кластер без дополнительных серверов управления. В production окружении рекомендуется использовать как минимум 4 сервера для отказоустойчивости .

2.2 Проверка статуса кластера

На клиенте (ALT Workstation):

Настраиваем клиент (если не настроен в первой работе)

Проверяем информацию о кластере

mcli admin info mycluster

Детальная информация о дисках

mcli admin info mycluster --json | grep -E "endpoint|state"

Ожидаемый результат: Должны отображаться три сервера, каждый с 4 дисками. Всего 12 дисков в кластере. Статус всех дисков — online.

Этап 3: Erasure Coding в действии — загрузка данных и отказоустойчивость

3.1 Загрузка тестовых данных

На клиенте (ALT Workstation):

Создаём тестовый файл (50 МБ)

dd if=/dev/urandom of=largefile.dat bs=1M count=50

Создаём бакет

mcli mb mycluster/test-bucket

Загружаем файл

mcli cp largefile.dat mycluster/test-bucket/

Проверяем, что файл загружен

mcli ls mycluster/test-bucket/

3.2 Понимание Erasure Code (EC) схемы

При 12 дисках (3 сервера × 4 диска) MinIO автоматически применяет схему Erasure Code. Стандартная схема для 12 дисков — EC:8 (8 шардов данных, 4 шарда чётности) или EC:6 в зависимости от версии.

Просмотр информации о пуле (EC схема)

mcli admin info mycluster

Более детальная информация о дисках

mcli admin heal mycluster --verbose

Вопрос: При схеме EC:8 сколько дисков может выйти из строя без потери данных? Почему это эффективнее, чем 3-кратная репликация?

Пояснение: Erasure Code разбивает каждый объект на n шардов данных и m шардов чётности. При EC:8 из 12 дисков 8 отведены под данные, 4 под чётность. Восстановление возможно при наличии любых 8 из 12 шардов. Значит, кластер может пережить отказ до 4 дисков (причём эти диски могут находиться на одном или разных серверах).

3.3 Симуляция отказа одного сервера

На ВМ2 (останавливаем контейнер):

docker stop minio-server

На клиенте (проверяем доступность данных):

Просмотр файлов (должен работать)

mcli ls mycluster/test-bucket/

Скачивание файла (должно работать)

mcli cp mycluster/test-bucket/largefile.dat restored-file.dat

Сверяем контрольную сумму

md5sum largefile.dat restored-file.dat

Проверяем статус кластера (один сервер offline)

mcli admin info mycluster

Вопрос: Работает ли доступ к данным? Сколько серверов осталось в кластере? Почему данные остались доступны?

Пояснение:Erasure Code распределяет шарды по всем дискам кластера. При отказе одного сервера (4 диска) теряется до 4 шардов. Для восстановления данных достаточно любых 8 из 12 шардов, поэтому отказ одного сервера не влияет на доступность данных. Минус — производительность может временно снизиться, так как восстановление будет использовать оставшиеся шарды .

3.4 Восстановление сервера

На ВМ2 (запускаем контейнер снова):

docker start minio-server

На клиенте (проверяем, что сервер вернулся):

mcli admin info mycluster
mcli admin heal mycluster

Пояснение: После восстановления отказавшего узла MinIO автоматически запускает процесс healing — восстановление недостающих шардов на этом узле. Процесс происходит в фоне без остановки обслуживания. Статус можно отследить командой mcli admin heal.

Этап 4: Горизонтальное масштабирование — добавление сервера

Самый важный этап: Мы создадим четвёртый сервер (клон) и добавим его в существующий кластер, увеличив ёмкость и производительность.

4.1 Подготовка четвёртого сервера

  1. Клонируйте ВМ3 в ВМ4
  2. Измените IP-адрес на ВМ4 на 192.168.56.111
  3. Создайте директории для дисков на ВМ4

На ВМ4

mkdir -p /data/minio/disk{1,2,3,4}

4.2 Остановка кластера для изменения конфигурации

Важно: В MinIO добавление нового пула серверов требует перезапуска кластера с новым списком узлов. Данные при этом не теряются.

На всех существующих серверах (ВМ1, ВМ2, ВМ3):

docker stop minio-server
docker rm minio-server

4.3 Запуск расширенного кластера (4 сервера, 16 дисков)

Эту же команду (скопировать и вставить) выполнить на ВМ2, ВМ3 и ВМ4!

4.4 Проверка расширенного кластера

На клиенте:

Проверяем информацию о кластере

mcli admin info mycluster

Ожидаемый результат: 4 сервера, 16 дисков. Общая ёмкость увеличилась на 33% по сравнению с кластером из 3 серверов.

Вопрос: Как изменилась схема Erasure Code после добавления сервера? Сколько дисков может выйти из строя в новой конфигурации?

Пояснение: При 16 дисках MinIO может использовать схему EC:12 (12 шардов данных, 4 шарда чётности) или аналогичную. Количество дисков, которое может выйти из строя, остаётся равным количеству шардов чётности (4), но общая ёмкость и производительность растут пропорционально количеству дисков .

4.5 Проверка старых данных

Проверяем, что старые данные по-прежнему доступны

mcli ls mycluster/test-bucket/
mcli cp mycluster/test-bucket/largefile.dat restored-after-scale.dat
md5sum largefile.dat restored-after-scale.dat

Пояснение: Добавление нового сервера не влияет на существующие данные. MinIO продолжает обслуживать старые объекты, а новые будут распределяться с учётом добавленных ресурсов. Для полной ребалансировки (перераспределения старых данных на новые диски) можно запустить команду mcli admin rebalance start mycluster, но это необязательно и занимает время.

Этап 5: Нагрузочное тестирование

5.1 Тестирование производительности

Продемонстрируем, что добавление сервера распределяет нагрузку.

На клиенте:

Загружаем несколько больших файлов

for i in {1..10}; do
    dd if=/dev/urandom of=file$i.dat bs=1M count=20
    mcli cp file$i.dat mycluster/test-bucket/
    echo "Uploaded file$i.dat"
done

Просмотр использования дисков

mcli admin info mycluster

Вопрос: Как вы думаете, на какие диски попали файлы? Распределяются ли они равномерно по новому серверу?

Пояснение: MinIO использует хеширование для равномерного распределения объектов по всем дискам кластера. Добавление нового сервера автоматически включает его во все будущие операции записи. Это обеспечивает линейную масштабируемость.

5.2 Мониторинг через веб-консоль

На клиенте откройте браузер и перейдите по адресу: http://192.168.56.108:9001

В веб-консоли можно увидеть:

  • Все серверы кластера и их статус
  • Использование дисков на каждом сервере
  • Текущие операции чтения/записи

Этап 6: Симуляция отказа двух серверов (по желанию, если осталось время)

На ВМ2 и ВМ3 (останавливаем контейнеры):

docker stop minio-server

На клиенте (проверяем):

Проверка доступности данных

mcli ls mycluster/test-bucket/
mcli cp mycluster/test-bucket/largefile.dat restored-after-two-failures.dat

Проверка статуса

mcli admin info mycluster

Вопрос: При отказе двух серверов (8 дисков) из 16 данные остались доступны? Почему?

Пояснение: При схеме EC:12 для восстановления достаточно любых 12 из 16 шардов. Отказ двух серверов (8 дисков) означает потерю 8 шардов, но если оставшиеся 8 дисков содержат 8 необходимых шардов данных, объект будет восстановлен. Однако если отказавшие серверы содержали критическое количество шардов данных, некоторые объекты могут стать недоступны. Это демонстрирует важность правильного планирования отказоустойчивости.

Этап 7: Очистка

На каждом сервере:

Останавливаем и удаляем контейнер

docker stop minio-server
docker rm minio-server

Опционально: очищаем данные

rm -rf /data/minio/*

На клиенте:

Удаляем тестовые файлы

rm -f largefile.dat restored-*.dat file*.dat

Выводы

  • MinIO позволяет легко масштабировать объектное хранилище путём добавления новых серверов (клонов ВМ) в кластер.
  • Для отказоустойчивости MinIO использует Erasure Code, распределяя шарды данных и чётности по всем дискам кластера.
  • При 12 дисках (3 сервера) кластер выдерживает отказ до 4 дисков (схема EC:8).
  • Добавление четвёртого сервера (16 дисков) увеличивает общую ёмкость и производительность, а схема EC автоматически перестраивается.
  • MinIO не требует отдельного сервера управления — кластер формируется автоматически при запуске с одинаковым списком узлов.
  • Процесс healing автоматически восстанавливает данные после возвращения отказавшего узла.
  • В отличие от традиционных RAID-массивов, Erasure Code работает на уровне объектов, а не блоков, что обеспечивает гибкость при добавлении новых серверов.
