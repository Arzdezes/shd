Лабораторная работа №2: Отказоустойчивость и масштабирование Ceph

Цель работы: Протестировать отказоустойчивость кластера Ceph при выходе из строя узлов и OSD, настроить высокую доступность виртуальных машин, добавить новый узел в кластер.

Подготовка

Убедитесь, что кластер из лабораторной работы №1 работает:

# На любом узле проверяем статус
ceph -s
pvecm status

# На всех узлах проверяем, что Ceph OSD активны
ceph osd tree

Этап 1: Тестирование отказоустойчивости Ceph

1.1 Текущая конфигурация кластера

# Выводим дерево OSD
ceph osd tree

# Выводим карту распределения PG
ceph pg stat

Ожидаемый результат: Например, 3 узла, на каждом по 2 OSD (всего 6 OSD), репликация 3 копий.

1.2 Симуляция отказа одного OSD

На узле, где находится отключаемый OSD:

# Останавливаем OSD (например, osd.0)
systemctl stop ceph-osd@0

# Проверяем статус кластера (на любом узле)
ceph osd tree
ceph -s

Вопрос: Что произошло с состоянием OSD? Как изменился статус кластера?

Восстановление OSD:

# Запускаем OSD обратно
systemctl start ceph-osd@0

# Наблюдаем за процессом восстановления
watch -n 1 ceph -s

Пояснение: Ceph автоматически обнаруживает падение OSD и начинает репликацию данных на другие OSD для восстановления нужного числа копий.

1.3 Симуляция отказа целого узла

На отключаемом узле (например, PVE-03):

# Выключаем узел (или просто останавливаем Ceph)
systemctl stop ceph-mon
systemctl stop ceph-osd

На любом работающем узле:

# Проверяем статус кластера
ceph -s
ceph osd tree

# Проверяем состояние PG (должны быть active+degraded)
ceph pg stat

Вопрос: Доступны ли данные при отказе целого узла? Какие PG перешли в состояние degraded?

Восстановление узла:

На отключённом узле:

systemctl start ceph-mon
systemctl start ceph-osd

На работающем узле наблюдаем за восстановлением:

watch -n 1 ceph -s

Этап 2: Настройка высокой доступности (HA) для ВМ

2.1 Настройка HA для виртуальной машины

Создадим тестовую ВМ на RBD-хранилище (как в работе №1) и настроим для неё HA.

Через веб-интерфейс PVE:

  1. Создайте ВМ на хранилище ceph-storage.
  2. Выберите ВМ в дереве.
  3. Перейдите на вкладку HA.
  4. Нажмите Add.
  5. В поле VM выберите ID созданной ВМ.
  6. Выберите политику "migrate" (или "failover").
  7. Оставьте "Request State" как "started".
  8. Нажмите Add или OK.

Через CLI:

# Включение HA для ВМ (например, ID 101)
ha-manager add 101

# Просмотр статуса HA
ha-manager status

Пояснение: В Альт Виртуализации PVE используется стек HA на основе pacemaker+corosync для автоматической миграции ВМ при отказе узла.

2.2 Тестирование HA

Запустим нагрузку на ВМ и смоделируем отказ узла.

На ВМ (или на хосте PVE, где работает ВМ):

# Подключаемся к консоли ВМ и запускаем длительную задачу
ping 8.8.8.8 > /dev/null &

На узле, где работает ВМ, отключаем сеть:

# Имитируем отказ узла
ip link set eth0 down
# Или (осторожнее!)
systemctl stop corosync

Наблюдаем за поведением HA:

# На другом узле мониторим HA
watch -n 1 ha-manager status

Вопрос: Что произошло с ВМ? На каком узле она перезапустилась? Сколько времени заняло восстановление?

Пояснение: При обнаружении отказа узла HA-менеджер перезапускает ВМ на другом узле. Это называется failover (отказоустойчивое переключение).

2.3 Восстановление и возврат ВМ

Возвращаем сеть на отключённом узле и наблюдаем:

ip link set eth0 up
systemctl start corosync

Проверяем, что кластер восстановил quorum:

pvecm status

Этап 3: Горизонтальное масштабирование

3.1 Добавление нового OSD

Имитируем добавление нового диска в один из узлов.

# На узле, где есть свободный диск (например, /dev/sdd)
pveceph osd create /dev/sdd

# Проверяем дерево OSD
ceph osd tree

Вопрос: Как изменилась ёмкость кластера? Как Ceph распределяет данные на новые OSD?

3.2 Добавление нового узла в кластер

Подготовка четвёртого узла (PVE-04):

  1. Установите Альт Виртуализация PVE на четвёртую ВМ.
  2. Настройте сеть (192.168.56.104).
  3. Добавьте записи в /etc/hosts на всех узлах.
  4. Добавьте узел в кластер Proxmox:
    5. pvecm add 192.168.56.101
  5. Установите Ceph на новом узле:
    6. pveceph install
  6. Добавьте монитор на новом узле:
    7. pveceph mon create
  7. Добавьте OSD на новом узле (если есть диски):
    8. pveceph osd create /dev/sdb

3.3 Проверка расширенного кластера

# Статус кластера Proxmox
pvecm nodes

# Статус Ceph
ceph -s
ceph osd tree
ceph df

Этап 4: Настройка CephFS

4.1 Создание MDS и пулов для CephFS

bash

# Создаём метаданные MDS (на любом узле)
pveceph mds create

# Создаём пул для метаданных
ceph osd pool create cephfs_metadata 64

# Создаём пул для данных
ceph osd pool create cephfs_data 128

# Создаём файловую систему
ceph fs new cephfs cephfs_metadata cephfs_data

4.2 Настройка доступа к CephFS

Через веб-интерфейс PVE:

  1. Перейдите в Datacenter → Storage → Add → CephFS.
  2. ID: cephfs-storage
  3. MDS: выберите созданный MDS.
  4. Path: / (корень)
  5. Content: выберите Container и VZDump backup file.

Или через CLI:

pvesm add cephfs cephfs-storage --mds pve-01 --path / --content container,vztmpl

4.3 Проверка CephFS

# Монтируем CephFS вручную для теста
mount -t ceph 192.168.56.101:6789:/ /mnt -o name=admin,secret=$(ceph auth get-key client.admin)

# Проверяем
df -h /mnt
ls -la /mnt

Пояснение: CephFS — это POSIX-совместимая файловая система поверх Ceph, которая может использоваться для хранения контейнеров LXC и бэкапов.

Этап 5: Бенчмаркинг производительности

5.1 Базовое тестирование производительности Ceph RBD

# Создаём тестовый образ
rbd create test-bench --size 1024 --pool vm-storage

# Бенчмарк
rbd bench vm-storage/test-bench --io-type write --io-size 4096 --io-threads 16 --io-total 1G

# Очистка
rbd rm test-bench --pool vm-storage

5.2 Сравнение с производительностью локального ZFS

# Создаём тестовый файл на локальной ФС
dd if=/dev/zero of=/tmp/test.bin bs=1M count=1024 conv=fdatasync
