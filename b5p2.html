Лабораторная работа №2: НастройкаNFS-сервера и клиента

Тема: Развёртывание NFS-сервера на ALT Server, настройка экспорта каталогов, подключение с ALT Workstation, эксперименты с опциями монтирования и отработка сценариев отказоустойчивости.

Цель работы: Научиться настраивать NFS-сервер (версии 3 и 4), правильно экспортировать каталоги с различными опциями, монтировать их на клиенте, понимать разницу между режимами sync/async, hard/soft, а также отработать поведение при отказе сервера.

Топология:

  • Сервер: ALT Server 11 (виртуальная машина)
  • Клиент: ALT Workstation 10.4 (хостовая система)

Подготовка

Важно: Для выполнения команд с правами администратора мы будем использовать su -.
Переключитесь в режим root на обеих машинах.

На сервере (ALT Server)

su -

На клиенте (ALT Workstation)

su -

1.1 Проверка сетевого взаимодействия

Прежде чем настраивать NFS, убедимся, что сервер и клиент видят друг друга.

На сервере:

ip a

Запомните IP-адрес сервера (например, 192.168.122.206).

На клиенте:

ping -c 3 <IP-адрес_сервера>

1.2 Установка необходимых пакетов

На сервере (ALT Server 11):

ALT Server 11 поставляется с Samba версии 4.21.9. Установим серверную часть:

apt-get update
>apt-get install nfs-server rpcbind
Пояснение: Пакет nfs-server содержит серверную часть NFS. rpcbind необходим для работы NFSv3 (преобразует RPC-вызовы в сетевые порты). Для NFSv4 rpcbind не обязателен, но мы будем использовать оба протокола.

На клиенте:

apt-get install nfs-clients
Пояснение: Пакет nfs-clients содержит утилиты для монтирования NFS-шар (mount.nfs, showmount) и инструменты для работы с блокировками (nfslock).

1.3 Проверка установки

На сервере:

systemctl status nfs-server
systemctl status rpcbind

Вопрос: В каком состоянии находятся сервисы? Если они не активны, как их запустить?

Пояснение: Сервисы должны быть активны. Если нет, запустите systemctl enable --now nfs-server rpcbind.

Этап 2: Создание каталогов для экспорта

2.1 Создание тестовых каталогов на сервере

На сервере:

Создаём каталоги с разными сценариями использования

mkdir -p /srv/nfs/{public,private,upload,backup}

Создаём тестовые файлы

echo "Public file from server" > /srv/nfs/public/readme.txt
echo "Secret data" > /srv/nfs/private/secret.txt
echo "Upload area ready" > /srv/nfs/upload/welcome.txt

Устанавливаем права для теста upload-каталога (доступ на запись всем)

chmod 777 /srv/nfs/upload

Вопрос: Почему для каталога upload установлены права 777? В каких случаях это оправдано?

Пояснение: Каталог upload будет использоваться для проверки возможности записи на NFS-шару. Права 777 — это упрощение для лабораторной работы. В реальной жизни лучше использовать группы и более тонкую настройку прав.

2.2 Создание структуры для NFSv4

NFSv4 рекомендует экспортировать все каталоги внутри одного корневого каталога (например, /exports) с помощью mount --bind. Это повышает безопасность и упрощает конфигурацию.

Создаём корневой каталог для NFSv4

mkdir -p /exports/{public,private,upload,backup}

Привязываем наши каталоги внутрь /exports

mount --bind /srv/nfs/public /exports/public
mount --bind /srv/nfs/private /exports/private
mount --bind /srv/nfs/upload /exports/upload
mount --bind /srv/nfs/backup /exports/backup

Проверяем

ls -la /exports/

Вопрос: Что делает команда mount --bind? Чем она отличается от символической ссылки?

Пояснение: mount --bind делает каталог доступным в другом месте файловой системы. В отличие от симлинка, он работает на уровне ядра и "невидим" для некоторых приложений, что важно для chroot-окружений и NFSv4.

Этап 3: Настройка экспорта (NFSv3 и NFSv4)

3.1 Редактирование /etc/exports

На сервере:

cat > /etc/exports << 'EOF'

# Экспорт для NFSv3 и NFSv4
# Корневой каталог для NFSv4 (должен иметь fsid=0)
/exports        <IP-клиента>(rw,sync,no_subtree_check,fsid=0,crossmnt)

# Детальные настройки для конкретных каталогов
/exports/public  <IP-клиента>(ro,sync,no_subtree_check)
/exports/private <IP-клиента>(rw,sync,no_subtree_check,root_squash)
/exports/upload  <IP-клиента>(rw,async,no_subtree_check,all_squash,anonuid=1000,anongid=1000)
/exports/backup  <IP-клиента>(rw,sync,no_wdelay,no_subtree_check)
EOF
Важно: Замените <IP-клиента> на реальный IP-адрес ALT Workstation (или используйте * для доступа со всех адресов в лабораторной среде).

Вопрос: Проанализируйте каждую строку. Что означают опции ro, rw, sync, async, root_squash, all_squash, no_subtree_check, fsid=0, crossmnt?

Пояснение:

  • ro / rw — разрешение на чтение или чтение и запись.
  • sync / async — синхронная или асинхронная запись. async быстрее, но при сбое можно потерять данные.
  • root_squash — при обращении пользователя root с клиента его права понижаются до анонимных (обычно nobody).
  • all_squash — все пользователи с клиента отображаются на анонимного.
  • anonuid/anongid — явное указание UID/GID для анонимного пользователя.
  • no_subtree_check — отключает проверку, находится ли запрошенный файл в экспортируемом подкаталоге (повышает производительность).
  • fsid=0 — указывает, что этот каталог является корневым для NFSv4.
  • crossmnt — позволяет клиенту "видеть" точки монтирования внутри экспортируемого каталога.

3.2 Применение конфигурации

Проверяем синтаксис

exportfs -v

Применяем изменения

exportfs -ra
Пояснение: Команда exportfs -r перечитывает /etc/exports и применяет изменения без перезапуска сервера. Ключ -a означает "все экспорты".

3.3 Настройка rpcbind для NFSv3 (если нужно)

Если планируется использовать NFSv3, убедитесь, что rpcbind слушает сетевые интерфейсы:

Проверяем настройки rpcbind

cat /etc/sysconfig/rpcbind

Если строка CONTROL_ARGS="-l" не закомментирована — закомментируйте её (это ограничивает работу rpcbind только loopback-интерфейсом)

Пояснение: В ALT Linux по умолчанию rpcbind может быть ограничен локальным интерфейсом из соображений безопасности. Для работы NFSv3 по сети эту опцию нужно отключить.

Если вносили изменения, перезапустите rpcbind и nfs-server

systemctl restart rpcbind nfs-server

3.4 Просмотр экспортированных ресурсов

Просмотр экспортов с сервера

exportfs -v

Просмотр с клиента (позже выполните на клиенте)

showmount -e <IP-сервера>

Вопрос: Виден ли на клиенте каталог /exports или только его подкаталоги?

Пояснение: При использовании NFSv4 с fsid=0 клиент видит и может смонтировать только корневой каталог /exports, а все подкаталоги будут доступны внутри него. При NFSv3 каждый каталог экспортируется отдельно.

Этап 4: Монтирование NFS на клиенте

4.1 Монтирование NFSv4

mkdir /mnt/nfs

Монтируем корень NFSv4 (все каталоги внутри)

mount -t nfs4 -o rw,hard,intr,timeo=300,retrans=3 <IP-сервера>:/ /mnt/nfs

Проверяем

ls -la /mnt/nfs/
Пояснение: При монтировании NFSv4 мы указываем сервер и корневой каталог (:), а все субэкспорты становятся доступны как подкаталоги. Опции hard,intr означают, что при потере сервера процесс будет ждать, но его можно прервать по Ctrl+C .
Вопрос: Что вы видите в /mnt/nfs/? Какие каталоги там присутствуют?

Отмонтируем корень NFSv4

umount /mnt/nfs

4.2 Создание точек монтирования на клиенте

На клиенте (ALT Workstation):

mkdir -p /mnt/nfs/{public,private,upload,backup}

4.3 Монтирование отдельных каталогов (NFSv3-стиль)

Без демона rpc-statd потребуется опция nolock при монтировании

systemctl start rpc-statd

Монтируем public (только чтение)

mount -t nfs -o vers=3,ro,hard,intr <IP-сервера>:/exports/public /mnt/nfs/public

Монтируем private (чтение-запись)

mount -t nfs -o vers=3,rw,hard,intr <IP-сервера>:/exports/private /mnt/nfs/private

Монтируем upload (для теста записи)

mount -t nfs -o vers=3,rw,hard,intr <IP-сервера>:/exports/upload /mnt/nfs/upload

Монтируем backup (с увеличенными таймаутами)

mount -t nfs -o vers=3,rw,hard,intr,timeo=600,retrans=5 <IP-сервера>:/exports/backup /mnt/nfs/backup

Пояснение: При использовании NFSv3 мы монтируем каждый каталог отдельно, указывая полный путь на сервере. Версию протокола явно задаём через vers=3.

4.4 Проверка монтирования

df -h | grep nfs

mount | grep nfs
Обратите внимание на строку монтирования? Какие опции используются по умолчанию?

Этап 5: Тестирование доступа и опций

5.1 Проверка режимов доступа

На клиенте:

Проверка public (ro — только чтение)

cat /mnt/nfs/public/readme.txt<
echo "test" > /mnt/nfs/public/test.txt
Вопрос: Удалась ли запись? Почему?

Проверка private (rw, но root_squash)

cat /mnt/nfs/private/secret.txt
echo "test by root" > /mnt/nfs/private/test.txt
"Отказано в доступе" ?

Поравим права на сервере

chown root:nobody /exports/private
chmod 775 /exports/private

И повторим тест на клиенте

echo "test by root" > /mnt/nfs/private/test.txt

Проверка прав на записанный файл

ls -la /mnt/nfs/private/test.txt

Вопрос: Кто является владельцем созданного файла? Почему не root?

Пояснение: Опция root_squash (включена по умолчанию) отображает пользователя root с клиента на анонимного пользователя (обычно nobody/nogroup или nobody/nogroup) на сервере. Это критически важно для безопасности.

Проверка upload (all_squash + anonuid/anongid)

echo "upload test" > /mnt/nfs/upload/upload.txt
ls -la /mnt/nfs/upload/

Вопрос: Кто является владельцем upload.txt? Какому реальному пользователю на сервере соответствует UID 1000?

Пояснение: all_squash отображает всех пользователей с клиента на анонимного. anonuid=1000,anongid=1000 задаёт конкретного пользователя на сервере (обычно первого обычного пользователя). Это удобно для upload-каталогов, куда могут писать все, но права на записанные файлы ограничены.

5.2 Тестирование async/sync

На сервере в другом терминале можно наблюдать за операциями ввода-вывода:

Установите пакет iotop для мониторинга (на сервере)

apt-get install iotop
iotop

На клиенте выполните запись большого файла в каталоги с разными режимами.

Вопрос: Как вы думаете, в каком режиме запись будет завершаться быстрее? Какой режим безопаснее при сбое питания сервера?

Пояснение: async (как в каталоге upload) позволяет серверу подтвердить запись до того, как данные реально попали на диск. Это быстрее, но при внезапном отключении питания данные могут быть потеряны. sync гарантирует, что данные записаны на диск перед подтверждением — медленнее, но надёжнее.

Этап 6: Поведение при отказе сервера

6.1 Тестирование hard/soft-монтирования

Создадим временное монтирование с разными опциями и сымитируем отказ сервера.

На клиенте:

Создаём тестовые точки монтирования

mkdir -p /mnt/test/hard
mkdir -p /mnt/test/soft

Монтируем с hard-опциями

mount -t nfs -o vers=3,hard,intr,timeo=5 <IP-сервера>:/exports/public /mnt/test/hard

Монтируем с soft-опциями

mount -t nfs -o vers=3,soft,timeo=5,retrans=2 <IP-сервера>:/exports/public /mnt/test/soft

6.2 Симуляция отказа

На сервере (остановим NFS):

systemctl stop nfs-server

На клиенте попробуйте обратиться к смонтированным каталогам):

Попытка чтения с hard-монтирования

ls -la /mnt/test/hard/

В другом терминале попробуйте

ls -la /mnt/test/soft/

Вопрос: Как ведёт себя система в каждом случае? Можно ли прервать команду Ctrl+C?

Пояснение:

  • hard-монтирование: Процесс "зависает" в ожидании сервера. Если задана опция intr, команду можно прервать Ctrl+C.
  • soft-монтирование: Команда завершается с ошибкой I/O после истечения таймаута и повторных попыток.

6.3 Восстановление сервера

На сервере:

systemctl start nfs-server
exportfs -ra

На клиенте:

Проверяем hard-монтирование (должно заработать автоматически)

ls -la /mnt/test/hard/

Выводы

  • NFS — мощный протокол для организации сетевого доступа к файлам в среде Linux.
  • ALT Linux предоставляет полную поддержку NFSv3 и NFSv4 через пакеты nfs-server и nfs-clients.
  • Ключевые опции экспорта: rw/ro, sync/async, root_squash/all_squash, no_subtree_check.
  • Опции монтирования hard/soft/intr определяют поведение клиента при отказе сервера.
  • Для NFSv4 рекомендуется использовать bind-монтирование и единый корневой каталог с fsid=0.
  • Правильная настройка squashing-опций критична для безопасности в многопользовательской среде.
