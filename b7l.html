Лекция 9. Объектные хранилища и API S3

Цель лекции: Познакомить студентов с концепцией объектного хранения, объяснить его отличие от блочного и файлового доступа, изучить архитектуру S3 API, разобрать примеры использования (MinIO, Ceph), а также рассмотреть сценарии применения объектных хранилищ в современной IT-инфраструктуре.

Введение

До сих пор мы говорили о двух основных способах организации хранения данных:

  • Блочное хранение (iSCSI, Fibre Channel): Клиент получает "сырой" диск, сам управляет файловой системой. Идеально для баз данных, виртуализации, где нужен низкоуровневый контроль.
  • Файловое хранение (NFS, SMB): Клиент получает доступ к иерархии папок и файлов. Удобно для пользователей, приложений, которым нужна привычная структура.

Но есть третий способ, который в последние 15 лет стремительно набирает популярность — объектное хранение (object storage). Вместо иерархии папок и файлов, данные хранятся как объекты в плоском пространстве — бакетах (buckets). Каждый объект имеет уникальный идентификатор (ключ) и содержит не только данные, но и метаданные (произвольные атрибуты).

Стандартом де-факто для объектного хранения стало API S3 (Simple Storage Service), разработанное Amazon и ставшее отраслевым стандартом. Сегодня мы разберём, как устроены объектные хранилища, познакомимся с S3 API и его реализациями (MinIO, Ceph RGW), а также поймём, почему объектные хранилища стали основой для облачных архитектур, бэкапов и хранения больших данных.

Часть 1. Что такое объектное хранение?

1.1 Отличия от блочного и файлового хранения

Характеристика Блочное Файловое Объектное
Единица хранения Блок (сектор) Файл Объект
Иерархия Нет (LUN) Да (папки, дерево) Нет (плоское пространство)
Метаданные Минимум Атрибуты файла (владелец, права) Расширенные, произвольные (key-value)
Доступ По LBA (логический адрес блока) По пути (path) По ключу (key)
Масштабирование Сложное (SAN, кластерные ФС) Среднее (NAS-кластеры) Горизонтальное (масштабируется до эксабайт)
Протокол iSCSI, FC, NVMe-oF NFS, SMB S3, Swift
Применение БД, ВМ, ОС Домашние папки, общие ресурсы Бэкапы, статика, большие данные, облака

1.2 Ключевые понятия объектного хранения

1. Объект (Object)

  • Это минимальная единица хранения. Объект состоит из трёх частей:
    • Данные (Data): Само содержимое (бинарное или текстовое). Размер объекта обычно ограничен (в S3 — от 0 байт до 5 ТБ, но рекомендуется загружать частями при больших объёмах).
    • Метаданные (Metadata): Пары "ключ-значение", описывающие объект. Могут быть системными (Content-Type, Content-Length, Last-Modified) и пользовательскими (x-amz-meta-*).
    • Уникальный идентификатор (Key): Строка, по которой объект доступен. Ключ может содержать символы /, что создаёт иллюзию иерархии, но технически это просто строка.

2. Бакет (Bucket)

  • Контейнер для объектов. Бакет — это корневое пространство имён, аналогичное "диску" или "разделу".
  • Имя бакета должно быть уникальным в пределах всего хранилища (в облаке AWS — глобально, в MinIO/Ceph — в рамках инсталляции).
  • Бакеты могут иметь собственные политики доступа, конфигурацию версионирования, репликации.

3. Плоское пространство имён (Flat Namespace)

  • В отличие от файловой системы с иерархией папок, объектное хранилище не имеет вложенных директорий.
  • "Папки" эмулируются через префиксы в ключах. Например, объект с ключом photos/2024/wedding.jpg — это просто объект с ключом, содержащим слеши. Клиентские утилиты (например, AWS CLI) интерпретируют такие ключи как структуру папок.

1.3 История: от Amazon S3 до открытых реализаций

  • 2006 год: Amazon запускает S3 (Simple Storage Service) — первый коммерческий объектный сервис. S3 стал фундаментом AWS и облачной модели в целом.
  • 2009 год: Rackspace запускает OpenStack Swift — открытую реализацию объектного хранилища.
  • 2011 год: Начинается разработка Ceph Rados Gateway (RGW) — объектного шлюза для распределённой файловой системы Ceph.
  • 2014 год: Запущен MinIO — легковесное объектное хранилище, совместимое с S3 API, которое стало популярным для on-premise развёртываний.

Почему S3 API стал стандартом?

  • Простота: REST API с минимальным набором операций (PUT, GET, DELETE).
  • Масштабируемость: горизонтальное масштабирование без ограничений.
  • Надёжность: 11 девяток (99.999999999%) долговечности данных в AWS (достигается за счёт репликации и erasure coding).
  • Эко-система: тысячи инструментов, библиотек, драйверов, поддерживающих S3 API.

Часть 2. Архитектура S3 API

2.1 Основные операции

S3 API — это RESTful интерфейс, работающий поверх HTTP/HTTPS. Каждый объект идентифицируется по URL:

https://{bucket}.{endpoint}/{key}
или в path-style (более старый формат): 
https://{endpoint}/{bucket}/{key}

Основные операции:

Операция HTTP метод URL Описание
Создать бакет PUT /{bucket} Создать новый бакет
Удалить бакет DELETE /{bucket} Удалить пустой бакет
Список объектов GET /{bucket}?prefix= Получить список объектов в бакете
Загрузить объект PUT /{bucket}/{key} Создать или перезаписать объект
Скачать объект GET /{bucket}/{key} Получить содержимое объекта
Удалить объект DELETE /{bucket}/{key} Удалить объект
Получить метаданные HEAD /{bucket}/{key} Получить метаданные без данных
Многокомпонентная загрузка POST /{bucket}/{key}?uploads Загрузить большой объект по частям

2.2 Аутентификация

S3 использует сигнатуру запроса (signature) для аутентификации, не передавая пароль в открытом виде.

Signature Version 4 (AWS4-HMAC-SHA256):

  1. Клиент создаёт канонический запрос (метод, URI, заголовки).
  2. Создаёт строку для подписи.
  3. Использует секретный ключ для вычисления HMAC-SHA256.
  4. Подпись добавляется в заголовок Authorization.

Пример заголовка:

Authorization: AWS4-HMAC-SHA256 
Credential=AKIAIOSFODNN7EXAMPLE/20250322/us-east-1/s3/aws4_request, 
SignedHeaders=host;x-amz-date, 
Signature=fe5f80f77d5fa3beca038a248ff027d0445342fe2855ddc963176630326f1024

2.3 Версионирование

S3 поддерживает версионирование объектов на уровне бакета. При включённом версионировании:

  • При загрузке объекта с существующим ключом создаётся новая версия.
  • Старая версия не удаляется, а остаётся доступной.
  • Операция DELETE создаёт маркер удаления, но не удаляет старые версии.

Это обеспечивает защиту от случайного удаления и перезаписи.

2.4 Жизненный цикл (Lifecycle Policies)

Позволяет автоматизировать управление объектами:

  • Перемещение: через N дней переместить объекты в холодное хранилище (Glacier, S3 Glacier Deep Archive).
  • Удаление: через M дней удалить объекты.
  • Очистка: удалить старые версии объектов после заданного периода.

Пример политики:

{
  "Rules": [
    {
      "Id": "MoveToGlacier",
      "Status": "Enabled",
      "Prefix": "",
      "Transitions": [
        {
          "Days": 30,
          "StorageClass": "GLACIER"
        }
      ]
    },
    {
      "Id": "DeleteOldVersions",
      "Status": "Enabled",
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 90
      }
    }
  ]
}

2.5 Классы хранения (Storage Classes)

S3 предлагает несколько классов хранения с разным балансом стоимости и доступности:

Класс Доступность Стоимость Задержка Применение
S3 Standard 99.99% Высокая мс Часто используемые данные
S3 Intelligent-Tiering 99.9% Средняя мс Данные с неизвестным паттерном доступа
S3 Standard-IA 99.9% Средняя мс Редко используемые данные (требующие быстрого доступа)
S3 One Zone-IA 99.5% Низкая мс Некритичные данные в одной зоне
S3 Glacier Instant 99.9% Низкая мс Долгосрочное хранение с быстрым доступом
S3 Glacier Flexible 99.9% Очень низкая минуты-часы Архивы, бэкапы
S3 Glacier Deep Archive 99.9% Минимальная часы Данные, доступные раз в год

Часть 3. Инструменты для работы с S3

3.1 AWS CLI

Основной инструмент для работы с S3 из командной строки.

# Настройка учетных данных
aws configure
# Вводим Access Key, Secret Key, регион (us-east-1), формат вывода (json)

# Создание бакета
aws s3 mb s3://my-bucket

# Список бакетов
aws s3 ls

# Загрузка файла
aws s3 cp localfile.txt s3://my-bucket/remote/path/

# Синхронизация папки (инкрементальная)
aws s3 sync ./local_folder s3://my-bucket/folder/

# Загрузка с правами публичного доступа
aws s3 cp image.jpg s3://my-bucket/images/ --acl public-read

# Получение объекта
aws s3 cp s3://my-bucket/file.txt ./downloads/

# Удаление
aws s3 rm s3://my-bucket/file.txt

# Удаление всего бакета (включая содержимое)
aws s3 rb s3://my-bucket --force

3.2 MinIO Client (mc)

MinIO предоставляет свой клиент, очень похожий на AWS CLI, но удобный для работы с любыми S3-совместимыми хранилищами.

# Добавление хоста (alias)
mc alias set myminio http://localhost:9000 ACCESS_KEY SECRET_KEY

# Создание бакета
mc mb myminio/my-bucket

# Копирование файла
mc cp localfile.txt myminio/my-bucket/path/

# Синхронизация
mc sync ./local_folder myminio/my-bucket/folder/

# Просмотр содержимого
mc ls myminio/my-bucket

# Получение объекта
mc cp myminio/my-bucket/file.txt ./downloads/

# Удаление
mc rm myminio/my-bucket/file.txt

3.3 GUI-клиенты

  • Cyberduck: Кроссплатформенный клиент с поддержкой S3.
  • s3browser: Популярный клиент для Windows.
  • Rclone: Утилита для синхронизации с облаками (поддерживает S3).

3.4 SDK для разработчиков

Практически для любого языка программирования есть библиотеки с поддержкой S3:

Python (boto3):

import boto3

# Создание клиента (можно указать endpoint для MinIO/Ceph)
s3 = boto3.client(
    's3',
    endpoint_url='http://localhost:9000',
    aws_access_key_id='minioadmin',
    aws_secret_access_key='minioadmin'
)

# Создание бакета
s3.create_bucket(Bucket='my-bucket')

# Загрузка объекта
s3.put_object(
    Bucket='my-bucket',
    Key='folder/file.txt',
    Body=b'Hello World',
    Metadata={'project': 'lab', 'user': 'student'}
)

# Получение объекта
response = s3.get_object(Bucket='my-bucket', Key='folder/file.txt')
data = response['Body'].read()

# Список объектов
objects = s3.list_objects_v2(Bucket='my-bucket', Prefix='folder/')
for obj in objects.get('Contents', []):
    print(obj['Key'], obj['Size'])

# Генерация подписанного URL (временный доступ)
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'my-bucket', 'Key': 'folder/file.txt'},
    ExpiresIn=3600
)

JavaScript (AWS SDK v3):

import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";

const s3 = new S3Client({ endpoint: "http://localhost:9000" });

await s3.send(new PutObjectCommand({
    Bucket: "my-bucket",
    Key: "hello.txt",
    Body: "Hello World"
}));

Часть 4. Реализации объектных хранилищ

4.1 MinIO

MinIO — это легковесное, высокопроизводительное объектное хранилище, полностью совместимое с S3 API.

Архитектура:

  • Написано на Go (один бинарный файл).
  • Может работать как один сервер (для разработки) или как распределённый кластер (для продакшена).
  • Использует erasure coding для защиты данных (аналог RAID, но на уровне объектов).
  • Поддерживает шифрование, репликацию, версионирование.

Запуск MinIO (Docker):

docker run -d \
  -p 9000:9000 -p 9001:9001 \
  -e "MINIO_ROOT_USER=minioadmin" \
  -e "MINIO_ROOT_PASSWORD=minioadmin" \
  -v /mnt/data:/data \
  minio/minio server /data --console-address ":9001"

Применение:

  • Разработка и тестирование S3-приложений.
  • On-premise хранилища для бэкапов (например, интеграция с Veeam, Rclone).
  • Хранение статики (контейнеров, артефактов CI/CD).
  • Edge-хранилища (например, в IoT).

4.2 Ceph Rados Gateway (RGW)

Ceph — это распределённая система хранения, предоставляющая три интерфейса: блочный (RBD), файловый (CephFS) и объектный (RGW).

Архитектура:

  • Ceph RGW — объектный шлюз, предоставляющий S3 и Swift API поверх Ceph-кластера.
  • Данные хранятся в распределённом пуле объектов (RADOS), который обеспечивает:
    • Репликацию (по умолчанию 3 копии).
    • Self-healing (автоматическое восстановление при сбоях).
    • Горизонтальное масштабирование до эксабайт.

Применение:

  • Крупные облачные провайдеры (OpenStack).
  • Корпоративные хранилища с требованиями к масштабируемости и надёжности.
  • Бэкапные инфраструктуры (например, для Kubernetes через Rook).

4.3 OpenStack Swift

Swift — это объектное хранилище от OpenStack, появившееся раньше Ceph RGW. Оно имеет собственный API, но также поддерживает S3-совместимость через прокси.

Особенности:

  • Акцент на высокую доступность и согласованность (eventual consistency).
  • Использует репликацию (не erasure coding по умолчанию).
  • Часто применяется в крупных телеком- и облачных инфраструктурах.

4.4 Сравнение реализаций

Характеристика MinIO Ceph RGW OpenStack Swift
Сложность развёртывания Низкая (один бинарник) Высокая (много компонентов) Средняя
Масштабируемость До нескольких петабайт До эксабайт До эксабайт
Защита данных Erasure coding Репликация (3x) или EC Репликация
Производительность Очень высокая (на NVMe) Высокая (с правильной настройкой) Средняя
S3-совместимость 100% (основная цель) Высокая Средняя (через прокси)
Применение Edge, разработка, on-premise Крупные облака, OpenStack Телеком, OpenStack

Часть 5. Сценарии использования объектных хранилищ

5.1 Бэкапы и архивы

Это самый массовый сценарий. Объектные хранилища идеально подходят для бэкапов благодаря:

  • Низкой стоимости хранения (особенно в холодных классах).
  • Возможности версионирования (защита от случайного удаления).
  • Горизонтальному масштабированию (бесконечный объём).

Инструменты:

  • Veeam Backup & Replication: поддерживает S3 в качестве целевого хранилища.
  • Rclone: синхронизация данных с S3.
  • Bacula, Amanda, Duplicity: интеграция с S3 через плагины.

5.2 Статический хостинг (веб-сайты)

S3 может служить хостингом для статических сайтов (HTML, CSS, JS, изображения). Бакет настраивается на публичный доступ, и сайт доступен по HTTP.

Преимущества:

  • Нет необходимости в веб-сервере.
  • Автоматическое масштабирование.
  • Низкая стоимость.

5.3 Data Lake и аналитика

Объектные хранилища стали основой для Data Lake — централизованных репозиториев для хранения больших данных в исходном виде.

Как работает:

  • Данные (структурированные, полуструктурированные, неструктурированные) загружаются в объектное хранилище.
  • Инструменты аналитики (Apache Spark, Presto, Athena) читают данные напрямую из S3, используя pushdown-оптимизации (читают только нужные партиции).

Преимущества:

  • Отделение хранения от вычислений (хранилище и аналитика масштабируются независимо).
  • Низкая стоимость хранения.
  • Поддержка форматов (Parquet, ORC, Avro) с оптимизациями.

5.4 Хранение артефактов CI/CD

Объектные хранилища используются для хранения:

  • Собранных бинарных файлов (артефактов).
  • Docker-образов (через Registry, который может использовать S3 как бэкенд).
  • Кэшей сборки.

5.5 Медиа-контент (видео, изображения)

Потоковая передача видео, хранение пользовательских изображений, CDN-интеграция. S3 часто используется в связке с CloudFront (AWS) или другими CDN для распределения контента.

5.6 Резервное хранилище для Kubernetes

Rook позволяет развернуть Ceph в Kubernetes, предоставляя S3-совместимое хранилище через RGW. MinIO Operator делает то же самое для MinIO.

Часть 6. Архитектурные паттерны и лучшие практики

6.1 Именование ключей для производительности

В ранних версиях S3 производительность зависела от префиксов ключей (для партиционирования). Современные реализации (включая MinIO и Ceph) используют хэширование, поэтому это не критично, но хорошая практика:

Плохо:

logs/2024-01-01.log
logs/2024-01-02.log
...

Лучше (добавлять случайный префикс):

logs/2024/01/01/log_abc123.log
logs/2024/01/01/log_def456.log

6.2 Multipart Upload для больших объектов

При загрузке объектов > 100 МБ используйте многокомпонентную загрузку:

  1. Инициализация загрузки (получаем UploadId).
  2. Загрузка частей (минимум 5 МБ каждая, максимум 10 000 частей).
  3. Завершение загрузки (сборка объекта).

В AWS CLI это автоматизировано:

aws s3 cp largefile.bin s3://bucket/ --multipart

6.3 Преимущества и ограничения

Преимущества:

  • Неограниченное масштабирование: Добавление новых серверов автоматически увеличивает ёмкость и производительность.
  • Доступность: Встроенные механизмы репликации, erasure coding.
  • Гибкость метаданных: Любые произвольные теги.
  • Экономичность: Возможность использовать холодные классы хранения.

Ограничения:

  • Нет POSIX-совместимости: Нельзя монтировать как обычную файловую систему (хотя есть FUSE-решения, но с ограничениями).
  • Eventual consistency: В распределённых реализациях (Amazon S3, Ceph) есть задержки между записью и чтением (хотя для одного объекта в S3 — read-after-write consistency).
  • Сложность транзакций: Нет операций переименования (rename) — только копирование + удаление.
  • Латентность: Выше, чем у локального блочного хранения.

Часть 7. Тенденции и развитие

7.1 S3 как универсальный интерфейс

S3 API становится не просто протоколом для объектного хранения, а универсальным интерфейсом:

  • S3-compatible storage: MinIO, Ceph, Pure Storage, NetApp, Dell EMC.
  • S3 в файловых системах: Amazon FSx для Lustre, Qumulo.
  • S3 для блочного хранения: AWS EBS Snapshots в S3.
  • S3 для бэкапов: Veeam, Commvault, Rubrik.

7.2 S3 Express One Zone

В 2023 году Amazon анонсировал S3 Express One Zone — класс хранения с миллисекундными задержками (в 10 раз быстрее Standard), предназначенный для высоконагруженных приложений, ML-тренировок, аналитики в реальном времени.

7.3 S3 как уровень хранения для AI/ML

Объектные хранилища становятся основой для хранения обучающих наборов данных и чекпойнтов моделей. Инструменты (PyTorch, TensorFlow) имеют встроенную поддержку S3.

7.4 Object Storage vs POSIX в контейнерах

В Kubernetes активно развиваются S3 CSI-драйверы, позволяющие монтировать бакеты как тома. Однако они не поддерживают все операции POSIX (например, rename, fsync), поэтому подходят для определённых классов приложений.

Резюме и вопросы

Ключевые выводы:

  1. Объектное хранение — это третий способ организации хранения, отличный от блочного и файлового.
  2. S3 API стал отраслевым стандартом, предоставляющим простой REST-интерфейс для работы с объектами.
  3. Основные понятия: бакет (контейнер), объект (данные + метаданные), ключ (идентификатор).
  4. MinIO — легковесная реализация для on-premise, Ceph RGW — для крупных масштабов.
  5. Объектные хранилища идеально подходят для: бэкапов, Data Lake, статического хостинга, хранения артефактов.
  6. Ключевые преимущества: горизонтальное масштабирование, гибкость метаданных, низкая стоимость.
  7. Ограничения: нет полноценной файловой иерархии, eventual consistency, высокая латентность.
